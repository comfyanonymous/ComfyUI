# lodx_dit — LoD sparse attention for a bidirectional DiT

`Qwen3.5-2B-Lodx` の LoD 読み出しを、MiniMax H3 の DiT 形状に移植したもの。
本体（`comfy/`）には一切手を入れていない自己完結のプロトタイプ。

```bash
python lodx_dit/test_lod_dit.py       # 受け入れテスト (pytest 不要)
python lodx_dit/bench_h3.py           # H3 実形状の単層ベンチ
python lodx_dit/bench_h3.py --tune    # タイル形状の再チューニング
python lodx_dit/bench_h3.py --long    # 362 フレーム形状も測る
```

## 何が変わったか

三層読み出し（選ばれたページの葉 / 未選択ページの要約 / 厳密に読む領域）と、
`top_pages >= n_pages` で dense に一致するという錨は**そのまま**。
DiT は自己回帰デコーダではないので、次の三点だけが変わる。

| | LLM (LoDx) | **DiT (ここ)** |
|---|---|---|
| KV キャッシュ | 所有・追記・巻き戻し | **無い**。K/V は毎層毎ステップ作り直し |
| 状態維持 | `sums_pos` / `catch_up` / `truncate` | **不要**。ページ和は 1 回の segmented reduction |
| 層 E | 直近トークンの因果 tail | **層 X: 先頭の条件トークン**（text/cond/ref/audio） |
| 局所性 | tail が自ページを厳密に保証 | **クエリブロックの自ページを強制選択** |

移植元の落とし穴 #1（`n_pages` をキャッシュ長から取ると未来が混ざる）と
#2（`truncate` のゼロ化を省くと二重計上）は、**この設計では表現できない**。

そのまま効いたもの: `pool="block"` の選択粒度、タイ＝小さいページ id 優先、
`KP*ps` が `BN` で割り切れない時の `inb` マスク（落とし穴 #4）。

## 実測 (AMD Radeon PRO W7900 / gfx1100, torch 2.13.0+rocm7.2, triton 3.7.1)

> 2026-08-15 の初回測定は **ドライバ 7.2 に対し PyTorch が rocm7.13 ビルド**という
> 不整合な環境で取ったもので、dense attention だけが 24.6 TFLOPS(peak の 21%)に
> 落ちていた。整合後 59.6 TFLOPS(2.4x)になり、GEMM は 55.4 -> 56.4 とほぼ不変。
> 下の値は全て整合後のもの。旧値(attn 8.42x / DiT 2.98x)は dense が不当に遅かった
> ぶん **約 1.6x 過大** だった。

H3 の attention 形状: `H=56, head_dim=128, MHA, 双方向, batch 1`。
行数は `PackedLayout` の式から: 1344x768 / 124 フレームで
video 37,296 + audio 414 + text ~300 = **S = 38,010**。

### attention 単体 (`select_block=64`)

| 設定 | S | kP | dense | LoD | **比** | read | 理想 | 実現率 |
|---|---|---|---|---|---|---|---|---|
| 1344x768/124f | 38,010 | 16 | 693 ms | 117 ms | **5.92x** | 6.2% | 16.1x | 37% |
| 1344x768/124f | 38,010 | **32** | 681 ms | **141 ms** | **4.82x** | 8.9% | 11.2x | 43% |
| 1344x768/124f | 38,010 | 64 | 688 ms | 189 ms | 3.64x | 14.3% | 7.0x | 52% |
| 1344x768/124f | 38,010 | 128 | 687 ms | 284 ms | 2.42x | 25.1% | 4.0x | 61% |
| 1344x768/362f | 109,362 | **128** | 6,294 ms | **1,103 ms** | **5.71x** | 10.4% | 9.6x | 59% |
| 1344x768/362f | 109,362 | 256 | 6,375 ms | 1,762 ms | 3.62x | 17.9% | 5.6x | 65% |

### カーネルの効率と残りの取りしろ

kP=32 の 141 ms の内訳:

| 段 | ms | 比率 |
|---|---|---|
| kernel (層 S+L) | 78.7 | 56% |
| merge / reshape | 23.6 | 17% |
| exact flash (prefix 714 行) | 19.5 | 14% |
| selection | 11.8 | 8% |
| page sums | 7.6 | 5% |

カーネルは **41.2 TFLOPS**、dense flash が 59.6 なので **69%**。
旧スタックでは両方が壊れて同率だったため「実現率 101%」に見えていたが、
flash だけが直った結果カーネル側の非効率が露出した。

### タイル調律 (RDNA3)

MI325X の「N 幅は広いほど良い(BN=128)」が RDNA3 では反転し、**両方の N 幅を
WMMA の下限まで狭める**のが最適。`block_n=8` は WMMA に intrinsic が無く
コンパイル不可なので 16 が下限。

| 設定 | kernel | TFLOPS |
|---|---|---|
| bn=64 block_n=32 w2 (CDNA3 由来の推定) | 117.6 ms | 24.4 |
| bn=16 block_n=16 w2 | 83.1 ms | 34.5 |
| **block_q=64 bn=32 block_n=16 w4** | **69.6 ms** | **41.2** |

**warp 数はクエリタイルに追随させる必要がある**: 32 幅では w4 が w2 より 40% 遅いが、
64 幅では w4 が w2 の **1.7x 速い**(73.4 対 125.9 ms)。最初のスイープで w4 が
一貫して悪く見えたのはこのため。128 幅は行き過ぎ(106 ms)。

`select_block` を 32 -> 64 に上げると全体で約 1.2x 速くなるが、これは
**選択粒度を粗くする＝品質に影響する変更**であり、速度側しか測っていない。

## ページの空間形状（`ordering.py`）

ページは常に「連続する ps 行」なので、ページが**何を覆うか**を変える方法は
トークンの並び順を変えることしかない。H3 は video 行をラスタ順で出す
（`_frame_grid` が `indexing="ij"` で meshgrid して flatten、
`comfy/ldm/minimax/model.py:77-119`）ので、1344 幅では 1 行 = `lw/2` = 42 トークン、
ps=64 のページは**幅 42・高さ 2 の細い帯**になる。

素直に (1,8,8) タイルにすると **悪化した**。42 が 8 で割り切れず、
端タイル（8×2）のせいでページ境界がタイル行とフレームの両方を跨いで漂うため。

| grid (T,H,W) | raster | (1,8,8) タイル | **best_tile** |
|---|---|---|---|
| (37, 24, 42) = 1344x768/124f | 192.3 | 234.3（悪化） | **(1,8,7) ps=56 → 56.0** |
| (107, 24, 42) = 362f | 194.4 | 235.7（悪化） | **(1,8,7) ps=56 → 56.0** |
| (37, 24, 24) = 768x768/124f | 80.0 | 64.0 | **(1,8,8) ps=64 → 64.0** |

数値はページ 1 枚あたりの平均 bounding box（セル数、低いほど良い、下限は ps）。

`best_tile` はグリッドを**正確に割るタイル**だけを候補にし、**アスペクト比を
サイズより先に**見る。正確なタイルの bounding box は必ず自分の面積に等しいので
体積の指標では 8×7 と 3×21 を区別できないが、attention の局所性は空間的に
ほぼ等方なので、細長い帯は要約の代表として悪い。
1344x768 では 8×7 = 56 が選ばれ、1008（1 フレームの行数）を割り切るので
**フレーム跨ぎのページも消える**。

並べ替えは q/k/v を同時に置換して出力を逆置換するだけなので attention の恒等変換。
dense 一致の錨は影響を受けず、変わるのは選択がどのページを選ぶかだけ
（テストで固定してある）。

## DiT 全体への反映

線形層 19.3B params / 50 層を実測 56.4 TFLOPS で割った値を分母に入れる。
新スタックでは attention(59.6) と GEMM(56.4) がほぼ同率なので、FLOPs 比の
見積もりがそのまま使える。

| 設定 | attn 時間比 | kP | attn 実測 | **bf16 全体** | **INT8 線形併用** | 上限 |
|---|---|---|---|---|---|---|
| 1344x768/124f | 57% | 16 | 5.88x | 1.90x | 3.20x | 2.32x |
| 1344x768/124f | 57% | **32** | 4.87x | **1.83x** | **3.01x** | 2.32x |
| 1344x768/124f | 57% | 128 | 2.42x | 1.50x | 2.22x | 2.32x |
| 1344x768/362f | 81% | **128** | 5.71x | **3.00x** | **4.21x** | 5.21x |
| 1344x768/362f | 81% | 256 | 3.57x | 2.39x | 3.10x | 5.21x |

短尺は線形層が床になるので上限の 79%、長尺は 3.00x。
kP を 32 -> 128 に上げるコストは DiT 全体で **1.22x 遅くなるだけ**(1.83x -> 1.50x)。

## 品質の A/B のしかた

ComfyUI 側に 2 ノード登録される（`custom_nodes/lod_attention/` 経由）。

**MiniMax H3 LoD Attention** (`model/patch/minimax`) — MODEL → MODEL。
これを挟むと DiT が疎に読む。**バイパスすれば何もパッチされない**ので、
同じ seed・同じサンプラーで dense の基準が取れる。ここが A/B の要で、
「ノード無し == 素の dense と bit 一致」をテストで固定してある
(`comfy_wrapper_is_a_passthrough_without_config`)。

解像度・フレーム数・条件行の位置はモデルから自動で導出するので入力は不要。
主なつまみ:

| | 既定 | |
|---|---|---|
| `top_pages` | 128 | 予算。LLM 版は 32k で dense に並ぶのに 128 が必要だった |
| `select_block` | 64 | 1 集合を共有するクエリ数。32 より 1.2x 速いが選択は粗い |
| `page_size` | 64 | フレームを割る空間ブロックに丸められる (1344x768 で 8x7=56) |
| `local_radius` | 0 | 自ページに加えて強制する隣接ページ数。-1 で強制を無効 |
| `tiled_pages` | true | ページを空間ブロックにする並べ替え |
| `start_percent` | 0.0 | 上げると序盤（構図が決まる高ノイズ域）を dense のまま残せる |

**Compare Image Batches (PSNR/SSIM)** (`image/compare`) — 2 つの IMAGE から
フレーム別 PSNR/SSIM、前半・後半の drift、最悪フレームのレポートと差分画像を出す。
1 つのワークフローに dense 側と LoD 側の 2 本のサンプラーを置き、この
ノードで受けるのが一番手数が少ない。

**数値だけでは決まらない。** 動画の知覚品質に PPL 相当の指標は無いので、
PSNR/SSIM は「どのフレームを見るべきか」を絞る道具として使い、
最終判断は目視になる。drift 行（前半 vs 後半の PSNR）は平均が隠すもので、
疎な読みが破綻するときは後半から崩れる。

### 実行コストの目安

W7900 1 枚・1344x768/124f では dense が 60 秒/step なので、30 step の
A/B ペアで約 1 時間。反復には 768x768/124f（S=22,026、26 秒/step）か
step 数を落とすのが現実的。

## まだ測っていない / 次

1. **品質。ここが最大の空白。** ここまでは速度と厳密一致だけで、dense 出力との
   差は一度も測っていない。`probe_h3.py` は実装済み（実 H3 の forward に hook を
   入れ、層/ステップごとに dense との相対誤差と attention 質量カバレッジを
   kP・順序別に記録する）だが未実行。合成テンソルは局所性が無く選択が
   ほぼランダムになるので使えない。
2. **`select_block=64` の品質影響**。速度は 1.2x 取れたが、選択粒度を粗くする
   変更なので品質側の裏付けが要る。タイル順序を入れた今なら 64 行は
   8x7 タイル 1 枚 + 8 行なので空間的まとまりは保てるはず、という理屈だけの状態。
3. **pre-RoPE 採点**（移植元 `docs/lodx-design.md` §11 の未解決仮説）。
   H3 は RoPE を attention 直前に in-place 適用し、キャッシュが無いので、
   rope 呼び出しの前に K を足すだけで実験できる。3 軸 RoPE なので
   位相打ち消しの影響は LLM より大きいはず。
4. **周辺段の融合**。kP=32 で merge/reshape が 17%、exact が 14%。先頭の条件行を
   カーネル内の「常時読む層」に畳み込めば LSE マージごと消える。
5. **MI325X での再測**。RDNA3 のタイル結論(N 幅を最小に)は CDNA3 には当てはまらない。
6. **ComfyUI への接続**。`optimized_attention` はページ構造を受け取れないので、
   `transformer_options` に layout descriptor を載せるのが唯一のフック
   （`comfy/ldm/minimax/model.py:184` が既に渡している）。
