# LoD Attention for a bidirectional DiT — 設計

移植元: `Qwen3.5-2B-Lodx`（さらにその元は `llama.cpp/docs/lod-attention-spec.md`）。
対象: MiniMax H3 の DiT（`comfy/ldm/minimax/model.py`）。

この文書は **何をどう作ったか、なぜそうしたか、どこが元の仕様から逸脱しているか**を書く。
実測値は `lod-dit-results.md` に分けてある。

---

## 1. 読み出し

クエリブロックごとに、**三つの層を単一の softmax** で読む。ここは仕様のままで、
式も変えていない。

| 層 | 内容 | logit |
|---|---|---|
| **X** 厳密 | 条件行（text / cond / ref / audio）と端数行 | `c·q·k_j` |
| **S** 要約 | 選ばれなかった完全ページ 1 枚につき 1 項 | `c·q·(Ks/ps) + log(ps)` |
| **L** 葉 | 選ばれた `top_pages` ページの実トークン | `c·q·k_j` |

**選ばれたページは要約を黙らせ、代わりに中身で参加する。** よって全トークンが分母に
ちょうど 1 回入り、`top_pages >= n_pages` なら **tier S が空になり dense と厳密一致**する。
この一致が唯一の正しさの錨で、テストで全経路に固定してある。

要約項が `sum_j exp(c·q·k_j)` の Jensen 一次近似であること、`ps` を和で持つことで
`log(ps)` が定数になること、端数ページを要約しないので「半分埋まった要約」が
**表現できない**こと — このあたりも仕様のままである。

---

## 2. DiT のために構造的に変えたところ

### 2.1 KV キャッシュが無い

DiT は毎層・毎ステップで K/V を作り直し、forward を跨いで保持しない。したがって
`LodxCache` とその状態機械が丸ごと不要になる。

| LoDx | ここ |
|---|---|
| `append` / `catch_up` / `truncate` / `sums_pos` | **すべて廃止** |
| ページ和は `scatter_add_` で逐次 fold | **1 回の segmented reduction** |
| 落とし穴 #1（`n_pages` をキャッシュ長から取ると未来が混ざる） | **表現できない** |
| 落とし穴 #2（`truncate` のゼロ化を省くと二重計上） | **表現できない** |

ページ和は `key[:, :, prefix:paged_end].reshape(b,h,n,ps,d).sum(3, dtype=torch.float32)`
の一発。ページが連続かつ完全なので `scatter_add_` は要らない。

### 2.2 層 E（因果 tail）→ 層 X（厳密 prefix）

LLM で tier E が存在したのは「直近トークンにはまだ完全なページが無い」ためだった。
DiT に「直近」は無い。代わりにあるのが**先頭の条件行**で、H3 のパックされた
シーケンスは

```
[ text | cond | ref | audio | video ]
```

の順（`PackedLayout.__init__`）。text 行を要約するとプロンプト追従が壊れるので、
ここは常に厳密に読む。**tier E と同じ「連続スライスを厳密に読む層」が、末尾から
先頭に移っただけ**である。最後の完全ページ以降に残った端数行もここに合流する。

`prefix` は「video 行以外すべて」として求まる。video が常に最後の segment なので、
`prefix = seq_len - video_rows` で足りる。

### 2.3 層 X をカーネルに統合

LoDx は tier E を flash で読み、S+L のカーネル結果と LSE でマージしていた。
ここでは三層とも同じカーネル内の online softmax に入れ、**カーネルが完成した結果を
返す**。速度はほぼ同じ（0.98〜1.03x）だったが、LSE マージと fp32 一時テンソル 2 本が
消えて構造が単純になったので残している。

## 3. 仕様に無い追加（本当の逸脱）

ここが LoDx と挙動が変わる部分。**同じ `top_pages` を指定しても読むものが違う。**

### 3.1 局所ページの強制選択

LLM では tier E が「クエリは自分の近傍を必ず厳密に読む」を保証していた。DiT に
その保証は無い — video 行はページの**内側**にいて、選択がそのページを拾わなければ
自分の近傍すら要約になる。動画の attention は局所性支配なので、これは効く。

対策として、**クエリブロックが占めるページを選択に強制的に含める**
（`_forced_pages`、`local_radius` で隣接ページまで広げられる、`-1` で無効）。
`pooled` の該当位置を `+inf` にするだけなので、`top_pages >= n_pages` の
全展開では何も変わらず、**dense 一致の錨は壊れない**。

### 3.2 ページを空間ブロックにする並べ替え（最大の逸脱）

仕様 §1 は `page(t) = floor(t / ps)` と「**セル番号 == 位置**」を不変条件に置く。
ここではその前提を崩し、**video 行を空間ブロック主順に置換**している。

理由: H3 は video 行をラスタ順で出す（`_frame_grid` が `indexing="ij"` で meshgrid
して flatten、`model.py:77-119`）。1344 幅なら 1 行 = `lw/2` = 42 トークンなので、
ps=64 のページは**幅 42・高さ 2 の細い帯**になる。上下に隣接するトークンが別ページに
飛び、ページ和の代表性が壊れる。

`ordering.py` が `(t, h//bh, w//bw, h%bh, w%bw)` で並べ替える。q/k/v を同時に置換して
出力を逆置換するので **attention としては恒等変換**であり、dense 一致には影響しない。
変わるのは「ページが何を覆うか」だけ。

**素直なタイル指定は失敗する。** (1,8,8) を H3 の 24×42 グリッドに当てると、42 が 8 で
割り切れず端タイル (8×2) が出て、ページ境界がタイル行とフレームの両方を跨いで漂う。
平均 bounding box は **192 → 234 セルと悪化し、ラスタ順に負ける**。

そこで `best_tile` は

1. **グリッドを正確に割るタイルだけ**を候補にする
2. **アスペクト比をサイズより先に**見る（正確なタイルの bounding box は必ず自分の
   面積に等しいので、体積の指標では 8×7 と 3×21 を区別できない。attention の局所性は
   空間的にほぼ等方なので細長い帯は代表として悪い）
3. 目標付近に何も無ければ、割り切れる中で最大のものを取る

`page_size` はその結果として決まる（**64 固定ではない**）。1344x768 なら 8×7 = 56 で、
1008（1 フレームの行数）を割り切るのでフレーム跨ぎも消える。

**ただし `bt=1` の決め打ちは誤りだった。** 「フレームは行より遥かに長いストライドなので
混ぜても得は無い」という理屈で時間軸を候補から外していたが、実活性値で測ると
**`4x2x7` が `1x8x7` を 9 セル中 9 セルで上回る**（全層平均 kP=32 で −12.4%）。
潜在フレームは既に時間圧縮されているので、1 潜在フレーム離れたトークンのほうが
数パッチ離れたトークンより似ている。上の理屈は逆だった。実測は results §6.1。
既定を変えると現行設定での品質評価が無効になるため未反映。

### 3.3 選択スコアの計算が違う

LoDx は `torch.einsum("bhqd,bhpd->bhpq", q, sums)` で `(B,H,P,S)` を実体化してから
head と block で max を取る。ここでは**融合カーネル**（`kernel.block_scores`）で
中間を作らずにブロック最大まで一気に出す。

副作用として**精度が変わった**。einsum は bf16 で累算するため、H3 のスコア規模
（|mean| ≈ 293、分散 ≈ 28）に対し平均 0.48 の誤差が乗る。

| | fp64 真値との誤差 | 真値の top-32 との一致率 |
|---|---|---|
| torch einsum（LoDx 相当） | mean 4.83e-01 | **80.3%** |
| 融合カーネル（ここ） | mean 2.79e-05 | **100.0%** |

**同じ `top_pages` でも選ばれるページが約 2 割違う。** LoDx の LLM での品質評価を
そのまま持ち込めない理由がこれ。

### 3.4 既定値

| | LoDx | ここ | 理由 |
|---|---|---|---|
| `select_block` | 32 | **64** | カーネルが 1.2x 速い（`BLOCK_Q` が `select_block` に縛られる）。選択は粗くなる |
| `page_size` | 64 固定 | **グリッド依存** | 3.2 参照 |
| `local_radius` | 無し | **0** | 3.1 参照 |

## 4. カーネル

`kernel.py` が本番、`kernel_exp.py` が実験用の別系統（ノードの `kernel_variant` で
切り替え、`VARIANTS` に足せば同じ受け入れテストが自動で回る）。

LoDx から引き継いだもの: online softmax の構造、`inb` マスク（落とし穴 #4）、
「逆量子化がループに無い」設計。

追加・変更:

- **head_dim 128 の対応**。元は `a0`/`a1` を決め打ちで `base` と `base+128` に store
  しており、128 幅のヘッドに 256 レーン書いていた（`D % 128` のガードが通してしまう）。
  H3 は `attention_head_dim=128` なのでこれが必要だった。
- **クエリタイルの巻き上げ**。元はループ内で毎回 q を読み直していた。単体では
  1.00〜1.03x にしかならなかったが、**`num_stages=2` を成立させた**（後述）。
- **RDNA3 向けの再調律**。CDNA3 の「N 幅は広いほど良い（BN=128）」が反転する。

### 4.1 律速はレジスタで、LDS ではない

gfx1100 で計測すると、どの構成も **LDS は 16 KB / 64 KB しか使わず、VGPR は 256 上限に
張り付く**。順位はスピル数に従う。

| 構成 | regs | spill | ms |
|---|---|---|---|
| bn=32 stages=1（巻き上げ前の調律） | 256 | 81 | 187.4 |
| bn=16 stages=1 | 256 | 0 | 185.3 |
| bn=32 stages=2 | 256 | 38 | 184.4 |
| **bn=16 stages=2**（現行） | 256 | **24** | **172.4** |
| bn=16 stages=3 | 256 | 99 | 189.9 |
| bn=32 stages=1 **warps=8** | 231 | **0** | 287.5 |

warps=8 はスピルゼロなのに 1.6x 遅い。波あたりのレジスタ予算が減って ILP が落ちる。
**「スピルを消せば速い」ではない。**

`block_n=8` はコンパイルできない（WMMA に N<16 の intrinsic が無い）。16 が調律の
選択肢ではなく**下限**。

## 5. 落とし穴（ここで踏んだもの）

LoDx の落とし穴 #1・#2 は構造的に消えたが、代わりに固有のものが出た。

1. **素数のグリッド**。`best_tile` が目標付近のタイルを見つけられないとき、旧実装は
   `(1,1,1) / page_size=1` を返していた。736x416 は grid 13 x 23 で**縦横とも素数**の
   ため、1 行 = 1 ページになり、42,458 ページ中 64 枚だけ葉で残り全部が要約 =
   **読み取り率 100.2%（dense より重い）**になる。割り切れる中で最大のものを取る
   フォールバックに変更した。回帰テストあり。

2. **サンプリング窓は percent では使えない**。H3 は `shift=12` なので sigma の分布が
   極端に偏る（percent 0.0〜0.8 が sigma 1.0〜0.75 に押し込まれる）。`start_percent=0.3`
   は「序盤 30% を dense に」のつもりが実際は**全ステップ LoD**、`end_percent=0.5` は
   **0 ステップ**になる。退化した窓は警告を出すようにしたが、**この 2 つは既定値
   （0.0 / 1.0）から動かさないのが安全**。

3. **非連続な q/k/v**。H3 は `q.transpose(0,1).unsqueeze(0)` を SDPA に渡す
   （`model.py:181`）。gfx1100 では 1344x768/124f で **2145 ms 対 765 ms** と 2.8 倍
   違う。ノードの `contiguous_qkv`（既定 on）が**両モードに**コピーを挿す。片側だけに
   入れると「LoD が速いのは連続化のおかげ」という交絡になるので、テストで固定してある。
   ただし S が小さいと差は消える（S=7,215 で 25.7 対 24.2 ms）。

4. **`_forward` は全ブロックに同じ `t_emb` / rope テーブルを渡す**。Pipeline 分割時、
   `x` と一緒に移すだけでは境界の**次の**ブロックで取り残される。各テンソルを独立に
   判定する必要がある。

5. **comfy-kitchen の HIP カーネルは「現在の CUDA デバイス」との一致を要求する**。
   テンソルを移すだけでは `BufferError: Can't export tensors on a different CUDA
   device index` になる。マルチ GPU では `torch.cuda.device(dev)` で囲む。

## 6. ComfyUI への接続

`comfy/ldm/minimax/model.py:184` が `optimized_attention` に `transformer_options` を
渡しているので、そこがフックになる。AGENTS.md が「呼び出し側は選択された attention
backend を opaque に扱え」としているため、**モデル本体は 1 行も変えていない**。

- `optimized_attention` のラッパが設定を `transformer_options` から読む
- `MiniMaxH3Model._forward` のラッパが、attention 側では知りようのない
  **video グリッド**を公開する
- 設定が無ければ両方とも素通し（テストで**ビット一致**を固定）

ノードは**出力ノード**にしてある。ComfyUI は出力に使われないノードを実行しないので、
キャンバスに置いただけで効くようにするにはこれが要る。`model` 入力は任意で、
繋げばその MODEL クローンだけに、繋がなければグローバルに適用される。

後から足した widget は**すべて optional** にしてある。必須で足すと、その入力が
無かった頃に保存されたワークフローが `missing a required input` で弾かれる
（AGENTS.md「ノード変更は既定で後方互換に」）。

## 7. 未検証

- **品質**。`top_pages` を下げたときの劣化の出方、`select_block=64` の影響、
  3.3 の選択精度改善が品質にどう効くか。`probe_h3.py` はタイル形状の比較には
  使ったが（results §6.1）、これらの軸ではまだ回していない。
- **タイルの異方性が実際に効くか**。`(1,1,23)` のような細帯に警告を出しているが、
  `page_extent` では正確なタイル同士を区別できないため、理屈からの警告に留まる。
  形の優劣そのものは実活性値で測れるようになった（results §6.1）。残る空白は
  「細帯の警告が実際の劣化と対応するか」。
- **CDNA3 での調律**。4.1 は gfx1100 の結果で、MI325X には当てはまらない。
- **Tensor Parallel**。量子化重みの分割可否は検証済み（`lod-dit-results.md` 参照）だが、
  通信帯域は未実測。
